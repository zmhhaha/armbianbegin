📐 OpenSpec MCP 接入

让 Codex、Claude Code、Cursor 这类 AI 编程工具直接读写你的 OpenSpec 规格库。不需要在本地装任何 OpenSpec 环境，加一个远程 MCP 就行。

四步走完

  1. 提交项目申请，等管理员审批

    打开 openspec.panghuer.top/project-requests，用 Casdoor 登录后填表：显示名称、slug、GitHub 公开仓库地址、默认 ref、脚本 profile、说明。

    提交后服务端会校验字段并自动建一个 Gitea Issue。管理员检查后加上 status:approved 标签，系统随即创建该项目的私有 Gitea OpenSpec store，把申请人加为 Admin，并在 Issue 里评论 projectId 和仓库地址。

    审批通过之前，下面的步骤拿不到可用的 projectId。Issue 地址就是你的进度条。
  2. 取一个 JWT

    打开 openspec.panghuer.top/token，用 Casdoor 登录（GitHub 或邮箱），页面直接显示你的 JWT 和复制按钮，并给出各客户端的配置命令。

    这个 JWT 就是你在 MCP 上的身份。权限完全以该项目的 Gitea 仓库 ACL 为准：viewer 能读、editor 能写、owner 才能归档。

  3. 写进你的 Codex / Claude Code

    把下面的命令里的 $CASDOOR_JWT 换成上一步拿到的 JWT：

    Claude Code

    claude mcp add --transport http openspec \
  https://openspec.panghuer.top/mcp \
  --header "Authorization: Bearer $CASDOOR_JWT"

    Codex CLI

    codex mcp add openspec --transport streamable-http \
  https://openspec.panghuer.top/mcp \
  --header "Authorization: Bearer $CASDOOR_JWT"

    Cursor / Windsurf / 其他支持远程 MCP 的工具

    设置 → MCP → 添加远程 MCP server：

    • URL：https://openspec.panghuer.top/mcp
    • Header：Authorization: Bearer <JWT>

    验证连通性

    curl -s -X POST https://openspec.panghuer.top/mcp \
  -H "Authorization: Bearer $CASDOOR_JWT" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize",
       "params":{"protocolVersion":"2025-06-18","capabilities":{},
                 "clientInfo":{"name":"test","version":"0"}}}'
  4. 按规范写

    接进来之后不要直接改代码。规范驱动的顺序是：先写 change（提案 + spec delta + 任务），校验通过、合并进主 specs，再照着自己写的 spec 实现。

    把这个顺序明确告诉你的 AI 工具，或者在项目里放一条规则，否则它多半会先写代码。

工具清单

工具必填参数权限说明
list_projects—任意已认证列出你可见的项目
list_specsprojectIdRead列出主 specs（返回 revision）
list_changesprojectIdRead列出 active changes（返回 revision）
get_changeprojectId, changeIdRead读 change 工件与 taskStatus
create_proposalprojectId, changeId, expectedRevisionWrite创建 change
update_proposalprojectId, changeId, expectedRevision, filesWrite更新已有 change 工件
validate_changeprojectId, changeIdWrite校验 change/spec
apply_specsprojectId, changeId, expectedRevisionWritedelta 合并进主 specs，保留 change
archive_changeprojectId, changeId, expectedRevisionAdmin归档 change

标准工作流

1. list_projects                → 找到 projectId
2. list_specs / list_changes    → 取当前 revision（乐观并发基准）
3. create_proposal              → changeId + expectedRevision +
                                  files = { "proposal.md": …, "specs//spec.md": … }
4. validate_change              → 确认 valid=true（失败按 message 修内容）
5. update_proposal              → 需要改时，用最新 revision
6. apply_specs                  → delta 合入主 specs
7. archive_change               → 归档（需 owner 权限）

几条要守的规矩

  • 写操作要带 expectedRevision。它来自上一步的读，过期会返回 409，重新读一次再写即可。
  • 幂等：写工具不传 Idempotency-Key 时，服务按「用户 + 项目 + 工具 + 参数」派生确定性键。所以超时重试同一次调用不会重复写入，换个参数就是新调用。
  • 先 spec 后码。字段名别乱起：用 ### Requirement + #### Scenario，场景写 WHEN / THEN / AND THEN。
  • 归档要 owner。editor 能写能校验，但归档需要 Gitea 仓库 owner 权限。
  • projectId 是唯一边界。客户端只传 projectId，服务端按 Gitea 仓库实时查 ACL；无权限一律 404（刻意不区分「不存在」和「无权」）。

常见错误

状态含义怎么办
401JWT 无效 / 过期 / aud 不符回 /token 重新取
404项目不存在，或你无权访问查 projectId；确认自己在该 Gitea 仓库里
409revision 过期，或幂等键与上次内容不一致重新读 revision 再写
422validate/archive 的内容不合法按返回的 message 修 spec 内容
503Gitea / DB / Vault 依赖不可用稍后重试
